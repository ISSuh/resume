**전략 1: 복합 샤드 키 (Compound Shard Key) - 말씀하신 아이디어**

가장 직관적인 방법은 MongoDB의 복합 샤드 키를 사용하는 것입니다. 샤드 키를 `{ bucket_id: 1, object_id: 1 }`로 설정합니다.

*   **동작 방식**: MongoDB는 샤드 키의 첫 번째 부분(`bucket_id`)을 기준으로 데이터를 그룹화하려고 시도합니다. 같은 `bucket_id`를 가진 문서들은 가급적 같은 샤드, 혹은 인접한 청크(chunk)에 모이게 됩니다. `object_id`는 그 그룹 내에서 데이터를 분산시키는 역할을 합니다.
*   **장점**:
    *   **효율적인 LIST**: `LIST bucket_A` 요청이 오면, MongoDB는 `bucket_id`를 보고 해당 데이터가 모여있는 특정 샤드(들)로만 쿼리를 라우팅할 수 있습니다. 모든 샤드를 다 뒤지는 것(scatter-gather)보다 훨씬 효율적입니다.
    *   **단순성**: 데이터 모델이 하나로 유지되어 관리가 비교적 간단합니다.
*   **단점**:
    *   **핫 버킷 한계**: 만약 하나의 버킷에 수십억 개의 객체가 있다면, 결국 해당 버킷의 데이터는 하나의 샤드가 감당할 수 있는 용량을 초과하게 됩니다. 이 경우 MongoDB가 해당 버킷의 청크들을 다른 샤드로 분산시키긴 하지만, 여전히 `LIST` 연산은 여러 샤드에 걸쳐 수행되어야 하고, 해당 버킷에 대한 쓰기/읽기 I/O가 소수의 샤드에 집중될 수 있습니다.

**전략 2: 별도의 인덱스 테이블/컬렉션 (Separate Index Collection) - 가장 확장성 있는 패턴**

1.  **Object 메인 테이블**:

    *   **내용**: 객체의 모든 메타데이터 (크기, 위치, 암호화 정보 등)

2.  **Bucket 인덱스 테이블**:
    *   **샤드 키**: `bucket_id` (또는 핫 버킷 방지를 위해 `{ bucket_id: 1, object_name: 1 }`)
    *   **목적**: 오직 빠른 `LIST` 요청 처리를 위함.
    *   **내용**: `{ bucket_id, object_name } -> object_id` 형태의 포인터 정보만 가볍게 저장합니다.

*   **동작 방식**:
    *   **객체 생성(PUT)**: 메인 테이블과 인덱스 테이블, **두 곳 모두에** 데이터를 써야 합니다. (이로 인해 트랜잭션 또는 결과적 일관성을 보장하기 위한 복잡성이 추가됩니다.)

    *   **버킷 목록(LIST)**: `bucket_id`를 가지고 인덱스 테이블만 조회합니다.
*   **장점**:
    *   **최고의 확장성**: `GET`과 `LIST` 워크로드가 물리적으로 분리되어 서로에게 영향을 주지 않고 독립적으로 확장될 수 있습니다.
*   **단점**:

### 해결책: `context`를 이용한 명시적 생명주기 관리

````go
func workerWithContext(ctx context.Context, taskCh <-chan Task) {

            return // 고루틴을 안전하게 종료합니다.

        case task := <-taskCh:
            // 작업 처리
        }
    }
}
````

---

**모범 답안 예시**

리더는 팔로워의 로그가 자신의 로그와 일치하지 않을 수 있다는 것을 항상 가정하고 동작합니다. 이 불일치를 해결하는 과정은 다음과 같습니다.

1.  **리더의 `AppendEntries` RPC 전송**:
    리더는 각 팔로워에 대해 `nextIndex`라는 값을 유지합니다. 이는 '해당 팔로워에게 다음에 보낼 로그 항목의 인덱스'를 의미합니다. 리더는 `AppendEntries` RPC를 보낼 때, 새로운 로그 항목(`entries`)과 함께 두 가지 매우 중요한 정보를 담아 보냅니다.
    *   `prevLogIndex`: `nextIndex - 1`, 즉 새로 보낼 로그 바로 이전 로그의 인덱스.
    *   `prevLogTerm`: `prevLogIndex`에 해당하는 로그 항목의 `term`.

2.  **팔로워의 일관성 검사**:
    팔로워는 `AppendEntries` RPC를 받으면, 자신의 로그에서 `prevLogIndex` 위치를 확인합니다.
    *   **성공 조건**: 만약 팔로워의 `prevLogIndex`에 로그가 존재하고, 그 로그의 `term`이 리더가 보내준 `prevLogTerm`과 일치한다면, 팔로워는 자신의 로그가 리더와 해당 지점까지는 일치한다고 확신할 수 있습니다. 이 경우, RPC에 담겨온 새로운 로그 항목들을 자신의 로그 뒤에 추가하고 리더에게 성공을 응답합니다.
    *   **실패 조건**: 만약 팔로워의 `prevLogIndex`에 로그가 없거나, 있더라도 `term`이 일치하지 않는다면, 이는 로그 불일치를 의미합니다. 팔로워는 RPC에 담겨온 로그를 추가하지 않고, 리더에게 **실패를 응답**합니다.

3.  **리더의 재시도 (백트래킹)**:
    팔로워로부터 실패 응답을 받은 리더는 해당 팔로워의 `nextIndex` 값을 **1 감소**시킵니다. 그리고 감소된 `nextIndex`를 기반으로 새로운 `prevLogIndex`와 `prevLogTerm`을 설정하여 `AppendEntries` RPC를 즉시 다시 보냅니다.

이 과정은 마치 리더가 팔로워의 로그를 뒤에서부터 한 칸씩 검사하며 "이 로그는 가지고 있니? 그럼 이건?" 하고 물어보는 것과 같습니다. 이 '백트래킹(Backtracking)' 과정을 반복하다 보면, 언젠가는 리더와 팔로워의 로그가 일치하는 지점(consistency point)을 반드시 찾게 됩니다.

일치점을 찾은 후에는, 팔로워는 그 지점 이후의 모든 불일치 로그를 삭제하고, 리더가 보내주는 올바른 로그들로 덮어쓰게 됩니다. 이 메커니즘을 통해 Raft는 클러스터 전체의 로그가 리더의 로그와 동일하게 유지되는 **로그 일치 속성(Log Matching Property)**을 보장합니다.

*   **결과**: 분석 단계가 끝나면, 시스템은 crash 시점에 커밋되지 않은 트랜잭션들의 목록과, 디스크와 내용이 다를 수 있는 페이지들의 목록을 알게 됩니다.

**2단계: 재실행 (Redo Phase)**

*   **목표**: 시스템 다운으로 인해 디스크에 기록되지 못했을 수 있는 **모든 변경 사항(커밋 여부와 무관하게)**을 다시 적용하여, 데이터베이스를 crash 직전의 상태로 되돌립니다. (내구성 보장)
*   **과정**: 분석 단계에서 파악한 '가장 오래된 더티 페이지'의 로그부터 WAL 끝까지 다시 스캔합니다.
    *   모든 변경 로그(e.g., `UPDATE`)를 만날 때마다, 해당 변경이 디스크의 데이터 페이지에 이미 반영되었는지 확인합니다.
    *   만약 반영되지 않았다면, 로그의 내용을 데이터 페이지에 그대로 다시 적용(replay)합니다.
*   **결과**: 이 단계가 끝나면, 디스크의 데이터는 crash 직전의 메모리 상태와 완벽히 동일해집니다. 여기에는 커밋되지 않은 트랜잭션의 '더러운' 변경사항도 포함됩니다.

**3단계: 실행 취소 (Undo Phase)**

*   **목표**: 2단계 결과에 포함된, 커밋되지 않은 '활성 트랜잭션'들의 변경 사항을 모두 되돌려서 제거합니다. (원자성 보장)
*   **과정**: 분석 단계에서 얻은 '활성 트랜잭션 목록'을 사용합니다. 각 활성 트랜잭션에 대해, WAL을 **역순으로** 스캔하면서 해당 트랜잭션이 남긴 변경 로그들을 찾아냅니다.
    *   변경 로그를 찾을 때마다, 그 변경을 되돌리는 '보상 로그(Compensation Log Record, CLR)'를 WAL에 기록하고, 실제 데이터 페이지에 Undo 작업을 수행합니다.
*   **결과**: 모든 활성 트랜잭션의 변경이 제거되고 나면, 데이터베이스는 마침내 일관성 있는 상태(마지막으로 성공적으로 커밋된 상태)로 완벽하게 복구됩니다.

**모범 답안 예시**

**문제점: 일반 모듈로 해싱의 '대재앙적 재해싱(Catastrophic Rehash)'**

캐시 서버가 4대(`N=4`)라고 가정해봅시다. 일반 모듈로 해싱은 `server_index = hash(key) % 4` 공식을 사용합니다. 이 방식은 평상시에는 잘 동작하지만, 서버가 1대 추가되어 5대(`N=5`)가 되는 순간 문제가 발생합니다.

*   **변경 전**: `key_A`는 `hash(key_A) % 4 = 2`번 서버에 저장됩니다.
*   **변경 후**: `key_A`는 `hash(key_A) % 5 = ?` 로 계산됩니다. 이 결과가 우연히 2가 될 확률은 매우 낮습니다.

결과적으로, 서버가 1대만 추가/삭제되어도 **거의 모든 키(약 80% 이상)가 다른 서버를 바라보게 됩니다.** 이는 캐시의 대규모 미스(Cache Miss)를 유발하고, 모든 요청이 원본 데이터베이스로 몰리는 '캐시 스탬피드(Cache Stampede)' 현상을 일으켜 시스템 전체에 장애를 유발할 수 있습니다.

**해결책: Consistent Hashing의 '최소한의 재배치'**

인석님께서 설명하신 대로, Consistent Hashing은 이 문제를 해결합니다.

1.  **해시 링(Hash Ring)**: 0부터 2^32-1까지의 숫자로 이루어진 가상의 원을 만듭니다.
2.  **서버 배치**: 각 서버의 ID(e.g., IP 주소)를 해싱하여 링 위의 한 점에 배치합니다.
3.  **키 매핑**: 데이터의 키를 해싱하여 링 위의 한 점을 찾고, 그 지점에서 **시계 방향으로 가장 가까운 첫 번째 서버**에 데이터를 저장합니다.

이 구조에서 서버 클러스터가 변경될 때의 이점은 극명합니다.

*   **서버 장애/축소**: 서버 `S3`가 다운되면, 오직 `S3`가 담당하던 키들만 영향을 받습니다. 이 키들은 이제 시계 방향의 다음 서버인 `S4`로 자연스럽게 매핑됩니다. `S1`, `S2`, `S4`가 담당하던 키들은 전혀 영향을 받지 않습니다.
*   **서버 확장**: `S2`와 `S3` 사이에 새로운 서버 `S_new`가 추가되면, 오직 `S3`가 담당하던 키들 중 `S_new`와 `S3` 사이에 위치하는 키들만 `S_new`로 재배치됩니다.

결론적으로, 서버가 추가되거나 삭제될 때 영향을 받는 키의 범위는 **전체 키의 `1/N`** 수준으로 최소화됩니다. 이는 대규모 분산 시스템의 안정성과 확장성을 보장하는 핵심적인 특성입니다.

또한, 말씀하신 **가상 노드(Virtual Nodes)**는 실제 서버 1개를 링 위의 여러 지점에 배치하여, 특정 서버에 부하가 쏠리는 것을 방지하고 데이터를 훨씬 더 균일하게 분산시키는 매우 중요한 기법입니다.
