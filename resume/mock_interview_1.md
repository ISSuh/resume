### 모범 답변 예시

이 '거대 메타데이터' 문제에 대한 가장 효과적이고 확장 가능한 해결책은 **'목록 파일(Manifest File)' 또는 '인덱스 객체(Index Object)'** 패턴을 사용하는 것입니다.

아이디어는 간단합니다. 수만 개의 블록 ID 리스트를 원본 객체의 메타데이터에 직접 저장하는 대신, **그 리스트 자체를 하나의 새로운 객체로 만들어 저장**하는 것입니다.

**동작 방식:**

1.  **파일 분할**: 사용자가 100GB 파일을 업로드하면, 시스템은 이전과 동일하게 파일을 여러 개의 블록(예: 4MB짜리 블록 25,600개)으로 분할하여 각각 데이터 스토리지에 저장합니다.
2.  **목록 파일(Manifest) 생성**: 시스템은 이 25,600개 블록의 ID와 순서가 담긴 **목록(Manifest)을 내용으로 하는 새로운 객체**를 하나 생성합니다. 이 목록 파일 객체 역시 데이터 스토리지에 저장됩니다.
3.  **원본 메타데이터 업데이트**: 이제 원본 객체(100GB 파일)의 메타데이터에는 더 이상 긴 블록 리스트가 들어가지 않습니다. 대신, 방금 생성한 **'목록 파일 객체의 ID'** 와 파일이 여러 조각으로 나뉘었다는 표시(플래그)만 간단하게 저장합니다.

**결과:**

*   **메타데이터 크기 문제 해결**: 원본 객체의 메타데이터는 파일 크기와 상관없이 항상 작고 일정한 크기를 유지하게 됩니다. MongoDB의 16MB 문서 크기 제한과 같은 문제를 완벽하게 피할 수 있습니다.
*   **확장성**: 이 방식은 재귀적으로 적용될 수 있습니다. 만약 파일이 너무 커서 목록 파일 자체의 크기가 문제가 될 정도라면, '목록 파일의 목록 파일'을 만드는 식으로 무한히 확장이 가능합니다.
*   **일관된 아키텍처**: 새로운 종류의 데이터베이스(RDB)를 도입할 필요 없이, 모든 것을 '객체'라는 단일 개념 안에서 처리할 수 있어 시스템의 복잡도가 낮아집니다.

이 방식은 실제로 AWS S3의 **멀티파트 업로드(Multipart Upload)** 기능이 동작하는 핵심 원리와 매우 유사합니다. 이처럼 시스템의 기본 구성 요소를 활용하여 문제를 해결하는 것이 더 우아하고 확장성 있는 설계로 이어지는 경우가 많습니다.

### 장점

1.  **압도적인 확장성 (Massive Scalability)**: 앞서 이야기한 것처럼, 메타데이터 크기 제한 문제를 해결하여 사실상 무한한 크기의 파일을 지원할 수 있게 됩니다. 이것이 이 패턴을 사용하는 가장 큰 이유입니다.
2.  **병렬 다운로드/스트리밍 최적화 (Parallel Download/Streaming)**: 클라이언트는 목록 파일을 먼저 받은 뒤, 그 안에 있는 블록 리스트를 보고 여러 블록을 동시에 병렬로 요청할 수 있습니다. 이는 대용량 파일의 다운로드 속도를 획기적으로 높여줍니다.
3.  **아키텍처의 일관성 유지 (Architectural Consistency)**: 새로운 컴포넌트나 데이터베이스를 도입하는 대신, '객체'라는 기존 시스템의 기본 단위를 재활용합니다. 이는 시스템의 복잡도를 낮추고 유지보수를 용이하게 합니다.

### 단점 및 한계

1.  **읽기 증폭 (Read Amplification)**: 가장 큰 단점입니다. 파일을 읽기 위해 최소 두 번의 읽기 작업이 필요합니다. 첫 번째는 '목록 파일'을 읽는 작업, 두 번째는 그 목록을 보고 실제 '데이터 블록'을 읽는 작업이죠. 이는 특히 파일의 특정 부분만 조금 읽으려고 할 때(Range-based Read) 지연 시간(Latency)을 증가시키는 요인이 됩니다.
2.  **원자성(Atomicity) 보장의 복잡성**: 객체를 삭제하거나 수정할 때 문제가 복잡해집니다. 예를 들어, 객체를 삭제하려면 '목록 파일 객체'와 그에 연결된 수많은 '데이터 블록 객체'들을 모두 삭제해야 합니다. 이 과정 중간에 시스템 장애가 발생하면, 일부 블록만 삭제되거나 혹은 아무도 참조하지 않는 '고아 블록(Orphan Block)'이 남아 저장 공간을 낭비하게 될 수 있습니다. 이런 작업을 원자적으로 처리하기 위한 추가적인 로직(예: 별도의 가비지 컬렉션 프로세스)이 필요합니다.
3.  **작은 파일에 대한 오버헤드 (Overhead for Small Files)**: 굳이 나눌 필요가 없는 작은 파일에 이 패턴을 적용하면, 불필요한 목록 파일을 만들고 읽기 증폭만 유발하는 비효율이 발생합니다. 따라서 보통은 특정 크기(임계값) 이상의 파일에만 이 패턴을 적용하는 방식으로 구현합니다.

결론적으로, 이 패턴은 대용량 파일 처리에 필수적인 강력한 확장성을 제공하지만, 그 대가로 읽기 지연 시간 증가와 데이터 관리의 복잡성이라는 트레이드오프를 감수해야 합니다.

### 모범 답변 예시

제가 가장 크게 성장했다고 느끼는 경험은, 이전에 담당했던 B2B 클라우드 서비스에서 발생했던 **간헐적인 API 타임아웃 이슈를 해결했던 프로젝트**입니다.

**1. 문제 상황:**
어느 날부터 특정 고객사들로부터 파일 업로드 마지막 단계에서 간헐적으로 실패한다는 보고를 받기 시작했습니다. 모니터링 시스템(APM)을 확인해보니, 특정 API 엔드포인트의 P99 응답 시간이 갑자기 수십 초까지 치솟았다가 정상으로 돌아오는 스파이크가 불규칙적으로 발생하고 있었습니다. 하지만 서버의 CPU나 메모리 사용률은 평소와 같이 안정적이어서 원인을 파악하기 매우 어려운 상황이었습니다.

**2. 문제 해결 과정:**
처음에는 데이터베이스의 Lock이나 Slow Query를 의심했습니다. 하지만 DB 모니터링 툴과 Slow Query 로그를 분석해도 특이점을 찾을 수 없었습니다. 그 후, 부하가 몰릴 때 외부 서비스(결제, 인증 등) 호출에서 지연이 발생한다고 가정하고 해당 구간의 타임아웃과 로깅을 강화했지만, 역시 직접적인 원인이 아니었습니다.

문제는 항상 높은 부하 상황에서 불규칙적으로 발생했기 때문에, 저는 **애플리케이션 내부의 리소스 경쟁** 문제일 것이라는 새로운 가설을 세웠습니다. 이 가설을 검증하기 위해, 운영 환경과 동일한 스펙의 스테이징 환경을 구성하고 부하 테스트를 진행하며 **JVM 스레드 덤프와 힙 덤프**를 뜨기 시작했습니다.

수차례의 테스트와 분석 끝에, 스레드 덤프에서 공통적인 패턴을 발견했습니다. 다수의 스레드가 특정 **Connection Pool 라이브러리의 `getConnection()` 메소드에서 BLOCKED 상태**로 무한정 대기하고 있었습니다. 코드를 깊이 파고들어 가보니, 특정 예외 케이스에서 DB 커넥션을 사용한 뒤 Pool에 반환(release)하지 않고 누락하는 로직이 숨어있었습니다.

평상시에는 문제가 없었지만, 트래픽이 몰리면서 해당 로직이 동시에 여러 번 호출되자 Pool의 모든 커넥션이 고갈(Leak)되었고, 이후의 모든 요청은 반환되는 커넥션이 없어 무한정 대기하다가 결국 타임아웃으로 실패했던 것입니다.

**3. 해결 및 성과:**
근본 원인을 파악한 뒤, 예외 처리 로직에 `finally` 블록을 추가하여 어떤 경우에도 커넥션이 반드시 반환되도록 코드를 수정했습니다. 또한, 재발을 방지하기 위해 Connection Pool 설정에 유휴 커넥션을 검사하고 누수된 커넥션을 자동으로 회수하는 옵션을 활성화하고, 현재 활성화된 커넥션 개수를 모니터링하는 대시보드를 추가하여 잠재적인 누수를 조기에 발견할 수 있도록 시스템을 개선했습니다.

배포 이후, 해당 API의 P99 응답 시간은 안정화되었고 더 이상 타임아웃 에러는 발생하지 않았습니다.

**4. 배운 점:**

1.  **쓰기 시점 (Write Operation):**
