  2. 데이터 전송 최적화
  "센서 데이터 전처리 경험으로 네트워크 대역폭과 배터리 제약을 고려한 데이터 압축, 배치 전송 등을 경험했습니다"
  "이런 경험이 현재 파일 업로드 최적화나 청크 단위 처리 설계에 도움이 되고 있습니다"
  3. 에러 처리 및 복구
  "클라이언트에서 네트워크 불안정이나 서버 장애 상황을 자주 겪어봤기 때문에, 재시도 로직이나 Circuit Breaker 패턴의 중요성을 잘 알고 있습니다"
  4. 사용자 경험 고려
  "클라이언트 사이드에서 사용자와 직접 마주하는 경험이 있어서, 백엔드 설계 시에도 최종 사용자 경험을 항상 고려하게 됩니다"
  이런 식으로 구체적인 경험과 현재 업무에의 적용 사례를 연결해서 답변하시면 좋겠습니다.

### 전체 시스템에서 성능 병목을 어떻게 분석할 것인가? (Object Storage 관점)
- 제가 보통 이슈에 대해 처리할때나 리펠토링을 위해 기본 동작을 분석할떄, 주로 탑다운 방식으로 진행합니다.
개선이 필요한 API 의 동작이 하나의 서버가 아닌 MSA 와 같이 여러 서비스로 구성되어있다면,
모니터링 시스템이나 APM 을 통해 각 지점에 대한 응답시간이나 에러들을 파악 하고 일단 지연시간이 긴 구간부터 시작하여 작은 구간으로 순서대로 확인합니다.
문제가 의심되는 특정 서비스가 있다면 좀더 상세히 확인하기 위해 pprof 와 같은 프로파일링 툴과 같은 유용한 도구를 사용해 병목지점을 추적합니다.

### 전체 시스템의 성능 분석을 어떤 과정으로 진행할 것인가?
- 먼저 정의를 해야할것 같습니다. 기존 사내에 목표로 정의된 SLO 을 기준으로 성능분석을 진행할건지, 아니면 별도로 어느 기준에 대한 성능을 측정할건지 정의를 해야할것 같습니다.
두먼째로는 정의된 기준에 대한 기본적인 성능을 확인할것 같습니다.
예를들어 파일 크기별 성능을 측정한다라고 가정한다면, 여러 파일 크기별로 테스트 파일을 업로드/다운로드하여 p95 레이턴시를 측정하거나 서버의 cpu, memory, disk, io 등 수치를 계측해야할것 같습니다.
이후 측정된 데이터를 기반으로 최적화가 필요하다고 판단되면 추가적으로 APM, 메트릭 수집중이거나 별도 모니터링 시스템이 구축되어있다면 해당 모니터링 정보와 golang 의 pprof 와 같은 프로파일링 툴로 기본적인 병목지점을 찾아나간뒤 이슈에대한 처리를 진행해야할것 같습니다.

  폴더에 대한 이동/복사처리시 사용자가 선택한 옵션에 의해 특정 옵션이 활성화된 폻더/파일에 대해서만 동작을 처리하는 기능이 있습니다.
  해당 동작 수행시 약 8초정도의 소요시간이 걸리고 있는 상황에서 구현사항을 확인해보니 해당 기능 구현에 대해 파일 스토리지 구성상 폴더 하위에 여러 하위 폴더가 존재할수 있는데 이를 반복문으로 처리하는 부분이 있어 N+1 이슈가 발생하고 있는 상확이였습니다.
  이를 수정하기 위해 쿼리를 수정해 batch 로 1차적으로 조회하고 이를 서버에서 필터링하여 N+1 이슈를 수정하여 약 6초 정도로 개선하였습니다.
    - 이때 batch 로 한번에 조회하는 데이터의 양은 점진적으로 값을 수정하는 방향으로 진행했습니다. 운영환경에서 해당 API 에 대한 모니터링을 통해 초기 지정한 값을 수정하여 지정하였습니다.
- 래거시 DB 쿼리 개선을 통한 처리성능 약 40% 향상
  - 주요 수정 내용은 SQL 개선을 통해 조회 성능을 향상시킨내용입니다.
  특정 유저의 즐겨찾기된 파일에 대한 처리에 대한 내용중 유저의 즐겨찾기된 파일 목록들을 조회하는 부분에 대한 쿼리가 있습니다.
  해당 부분에 대해 파일,폴더,즐겨찾기,권한 과 같은 여러 테이블을 조인하도록 되어있는 쿼리였는데, 해당 쿼리에서 특정 회사의 유저의 경우 소요시간이 최악의 경우 약 9초정도 걸리던 이슈가 있었습니다. 해당 쿼리를 검토하기 위해 Explain 정보를 토대로 현재 쿼리에 대한 기본적인 정보를 조회하였고 부하테스트를 통해 해당 케이스에 대한 기본 TPS 를 측정했습니다.
  크게 두가지 사항을 적용하여 개선을 진행했는데, 먼저 많은 row 를 필터링할수 있도록 쿼리의 join 의 순서를 변경하면서 각 테이블에 적용된 인덱스를 사용하도록 수정했습니다.
  그리고 조회를 모두 쿼리로만 처리하는것이 아닌 일부분은 서버에서 처리하도록 수정했습니다.
  해당 쿼리를 호출하기전 기본적으로 권한에 대한 처리는 진행하므로 해당 파일에 대한 권한은 이미 알고있는 상태였습니다. 이를 이용해 굳이 쿼리에 권한관련 내용을 join 하지 않고 일단 모두 조회한후 서버에서 개별 처리를 진행하였습니다. 해당 내용들을 이용하여 결과적으로 해당 이슈 케이스에서 쿼리의 소요시간을 약 5초정도로 줄일수 있었습니다.
- 레거시 Batch 에 대해 비동기 병렬처리구조로 리펠토링 진행하여 소요시간 70% 단축
  - 입사후 아직 프로젝트에 대해 알아가고 있던중, 새벽마다 평균 1 ~ 5만개 정도의 다량의 파일을 특정 폴더로 이동시키는 Batch 프로세스 서비스가 있었고 확인해보니 해당 서비스의 동작시간이 10시간이 넘을 때가 많아 일상 업무시간인 9시를 넘어서 동작할때가 많았습니다. 아무래도 서비스의 특성상 일반적인 업무 시간인 9시 ~ 6시 동안 대부분의 트래픽이 집중되는데 해당 Batch 프로세스 서비스또한 해당 시간에 동작하게 되면 문제가 발생할수 있다고 생각하여 개선 작업을 요청하고 진행하게 되었습니다.
  기본적인 구조를 확인해보니 대상 파일을 처리하고 외부 이동 처리 서비스에 요청하여 특정 폴더로 이동시키는 구조를 하고 있는데, 이때 매 파일마다 동기/blocking 으로 이동시키는 것을 확인하였습니다. 해당 지점을 병목지점으로 판단하여 해당 처리를 병렬처리 그리고 비동기 처리 구조로 순차적으로 변경을 진행하였습니다. 초기에는 단순 gorouine 부터 시작했지만 추후 worker pool 을 도입하여 병렬처리로 구조를 개선하였습니다. 초기에는 5개정도의 worker 로 시작해서 모니터링을 진행하며 점진적으로 10개의 worker 로 늘려 처리 시간을 40% 정도로 개선하였으나, 그래도 가끔 업무시간까지 동작할 때가 있어 한번더 개선을 진행하였습니다. 이후에는 현재 병렬처리에 요청시 비동기를 추가하여 비동기 구조로 한번더 수정을 진행하였습니다. 그리고 무분별한 요청으로 인하여 외부 서비스에 영향이 발생하는 케이스에 대해 조절하고자 외부 이동 서비스의 최대 TPS 기준으로 1/3 정도를 기준으로 삼아 rate limit 울 통해 비동기 구조를 적용하였습니다. 결과적으로 기존 10시간이 넘을때가 많던 서비스를 3시간안에 동작하도록 수정하여 주요 트래픽 발생시간전에 처리하도록 개선할수 있었습니다.
    - 이동 요청 실패에 대해선 초기엔 지수 백오프 방식으로 점진적으로 retry 시간을 늘려가며 재시도 트라이를 구현하려했으나 기획적인 부분에서 해당 서비스는 에러 발생시 사용자에게 메일로 고지정도만 하는것으로 기획되어있어 해당 부분은 생략했습니다.
    - TPS 의 1/3?
      - 새벽 시간이라 비교적 트래픽에 여유롭지만 그래도 처리량을 모두 점유할수 없으므로 여유를 두어 해당 수치로 결정
- 대규모 파일 Cold Storage 적용을 위한 서비스 구조 설계 및 구현
  - 최근에 진행한 프로젝트입니다. 현재 파일 스토리지 서비스에서 실제 저장하는 부분은 S3 에 저장하는데, 공유 파일 특설상 오래된 파일을 ColdStorage 로 아카이빙하고 저렴하게 이용하도록 하는 서비스 입니다. 
  구현된 내용에 대해 좀더 디테일하게 설명하면 일단 파일 냉동 처리의 경우 스토리지클래스의 최소 과금정책으로 파일 크기별로 스토리지클래스를 나누어 냉동처리를 하였습니다.
  서비스에 대한 서버측 구현은 초기에는 기존 동작하는 각 서버에 추가기능으로 구현하여 냉동을 처리하였으나, 대용량,다량의 파일에 대한 처리를 위해 기존 서버 외 별도 냉동/해동 처리하는 서버를 구성하였습니다. 이동/업로드시 파일의 냉동은 다량의 파일을 처리할수 있도록 SQS 를 통해 냉동요청을 처리하고 별도의 냉동 서버에서 각각의 요청을 처리하여 개별적으로 냉동처리를 진행하도록 구현했습니다. 해동의 경우에는 S3 의 해동 이벤트를 SQS 와 연결하여 해동 메세지를 순차적으로 처리하고 그룹핑하여 해동이 완료된 파일들은 지정 목적지로 파일을 이동하시도록 구현하였습니다.
    - 비용절감에 대해선 아직 이제 해당 기능을 베타를 출시하여 실질적인 비용은 모르나 개발시작할때 예상 비용절감에 대해선 S3 비용에 대해 약 10% ~ 20% 수준으로 비용을 절감할수 있다고 판단하였습니다.
- ElasticSearch 비용 절감을 위한 Warm/Cold Storage 적용방안 수립
  - 기존 로그 데이터가 지속적으로 쌓이고 있고 해당 로그들을 지속적으로 활성화 상태로 남기는게 비용적으로 비효율적이라고 판단하여 3년이 지난 로그에 대해
  Warm storage 로, 5년이 지난 로그는 Cold Storage 로 저장하도록 하는 방안입니다.

- 시스템의 통계 데이터 수집을 위한 EalsticSearch 인덱스 설계 및 구현
  - 기본 구조는 하루에 한번 새벽에 batch 를 통해 DB 나 ElasticSearch 내 로깅된 데이터를 수집하여 서비스에 가입된 회사별로 특정 기능의 사용량,

  또한 저장되는 데이터를 생각해볼때 인덱스내 저장되는 개별 문서의 크기는 평균 약 2KB 정도이고, 하루평균 통계 수집되는 회사의 양은 특정 기능을 활성화 하는 회사는 특정 기능을 활성화한 회사만 대상이므로 약 1000개 정도의 회사 입니다. 즉, 매일 2MB 정도의 데이터가 쌓이게 되는데 사실 이는 RDB나 ElasricSearch 크게 상관없는 데이터양이지만, 추후 확장을 위해 ElasricSearch 를 사용했습니다. 현재는 특정 기능 혹은 전반적인 내용만 데이터를 수집하고 있으나 추후 새로운 기능이 추가되면 아무래도 비교정 모델링이 유연한 ElasricSearch 를 사용하는것이 좋다고 판단했습니다. 또한 이미 로깅에 ElasricSearch 를 사용하고 있으므로 저 이외 타 동료에게도 ElasricSearch 가 더 익숙한 기술스택이므로 MongoDB 와 같은 타 NOSQL DB 보단 ElasricSearch 를 선택했습니다.
    - 인덱스의 설계

## 개인 프로젝트

### Key/Value Storage 관련

- 프로젝트 설명
  - 해당 프로젝트는 LevelDB 와 같은 K/V storage 를 구현하고자 하는 목표에서 시작하였습니다.
  실질적으로 데이터를 저장할때 어떠한 기술로 저장하는지 확인하고자 했습니다.
  바퀴는 재발명하지 말라했지만, 기본이 되는 LSM-tree 기반 스토리지 엔진과 1차 memtable 구현을 위한 skiplist, 검색 최적화를 위한 bloom-filter, restore 를 위한 WAL, 추후 분산처리를 위한 RAFT 구현등 일반적으로 사용되는 기술들을 직접 구현하고자 했습니다.
    - 각 기술에 대한 선택이유
      - LSM-tree
        - 초기 프로젝트를 진행하면서 데이터 저장을 위한 주요 알고리즘들중 B-tree, lsm-tree, radix tree 들중 어느걸 기준으로 스토리지 엔진을 구현할까 고민하였습니다.
        그중 쓰기 중심 워크로드 특성과 현대 스토리지 시스템의 요구사항을 고려하여 LSM-tree를 선택했습니다.
          1. LSM-Tree (Log-Structured Merge Tree)
            - 어떻게 생겼냐:
            LSM-Tree는 쉽게 말해서 **“메모리에서 막 쓴 뒤, 나중에 디스크에 몰아서 정리하는 구조”**예요.
            쓰기 작업을 바로 디스크에 쓰지 않고, 먼저 **메모리(Memtable)**에 기록하고, 일정량 쌓이면 SSTable이라는 디스크 파일로 flush합니다.
            그리고 디스크에 쌓인 파일들은 **레벨(Level)별로 병합(compaction)**하면서 정리되죠.
            - 장점:
            쓰기가 엄청 빠릅니다. 왜냐하면 디스크에 랜덤하게 쓰지 않고, 순차적으로 몰아서 쓰기 때문이에요.
            그래서 로그나 NoSQL처럼 쓰기 위주 데이터베이스에서 최적화돼 있어요.
            - 단점:
            읽기는 조금 느릴 수 있어요. 이유는, 같은 key가 여러 SSTable에 흩어져 있을 수 있어서 여러 파일을 뒤져야 찾는 경우가 생기거든요.
            그리고 병합(compaction)을 할 때, 같은 데이터를 여러 번 다시 쓰기 때문에 **쓰기 증폭(write amplification)**이 발생합니다.
            - 왜 이런 장단점이 생기냐:
            특징이 쓰기 최적화 구조이기 때문이에요. “메모리에 먼저 쓰고, 디스크는 순차적으로 나중에 합친다” → 쓰기는 빠른 대신, 읽기는 여러 파일를 뒤져야 해서 느려질 수 있음.
            병합 과정에서 같은 데이터를 반복해서 쓰기 때문에 디스크 입출력이 많아짐 → 쓰기 증폭 발생
          2. B-Tree
            - 어떻게 생겼냐:
            B-Tree는 쉽게 말해서 **“균형 잡힌 트리 구조”**입니다.
            디스크 페이지 단위로 노드를 만들어서 **검색, 삽입, 삭제 모두 O(log N)**로 보장하죠.
            노드가 가득 차면 split 하고, 비면 merge 하는 방식으로 항상 균형을 유지합니다.
            - 장점:
            읽기/쓰기 모두 안정적인 성능을 보여줍니다.
            범위 검색(range query)도 잘 되고, 트랜잭션 DB에서 표준으로 쓰여요.
            - 단점:
            쓰기 성능은 LSM-Tree보다 느릴 수 있어요. 왜냐하면 노드 split, 재균형 작업이 필요하거든요.
            디스크 랜덤 접근이 많으면 SSD가 아닌 하드디스크에서는 느릴 수 있음.
            - 왜 이런 장단점이 생기냐:
            특징이 항상 균형을 유지하는 트리 구조이기 때문이에요.
            균형 덕분에 읽기는 항상 빠르고 예측 가능하지만, 쓰기할 때마다 균형을 잡아야 해서 비용이 발생함.
          3. Radix Tree (Trie)
            - 어떻게 생겼냐:
            Radix Tree는 key를 문자나 비트 단위로 쪼개서 트리로 저장하는 구조예요.
            예를 들어 “apple”이라는 key가 있으면 ‘a’ → ‘p’ → ‘p’ → ‘l’ → ‘e’ 이런 식으로 한 글자씩 내려가는 트리를 만드는 거죠.
            - 장점:
            Prefix 검색이 매우 빠릅니다. “app”으로 시작하는 모든 key를 바로 찾을 수 있어요.
            메모리 내에서 key lookup 속도가 매우 빠릅니다.
            - 단점:
            메모리 사용량이 많아요. 각 글자마다 노드를 만들어야 하니까요.
            임의 key lookup은 길이에 따라 성능이 달라질 수 있고, 범위 검색(range query)에는 적합하지 않아요.
            - 왜 이런 장단점이 생기냐:
            특징이 key를 문자 단위로 분리해서 계층적으로 저장하기 때문이에요.
            글자 단위로 쪼개서 빠르게 찾을 수 있지만, 노드가 많아 메모리 사용이 커지고, 범위를 순차적으로 조회하려면 트리를 한 글자씩 내려가야 해서 불편함.
      - skiplist
        - memtable 을 구현할때 흔히 사용되는 방식중 하나인 AVL tree 과 비교하여 어떤걸 구현할지 고민했으나
      상대적으로 구현이 용이하고 write 시 리벨런싱이 불필요하여 상대적으로 가벼고 추후 병렬처리의 구현 용이성을 위해 skiplist 를 선택하여 구현하였습니다.
      - WAL
        - K/V 스토리지나 RAFT 를 구현하면서 장애시 복구에 대한 방안을 검토해보다 일반적으로 많이 쓰이는 방식인 WAL 에 대해 확인하여 해당 내용도 구현하였습니다.
      - RAFT
        - 분산처리 환경에서 흔히 사용되는 로직에 대한 스터디를 위해 구현
      - Bloom Filter
        - LSM-tree 의 경우 b-tree 에 비해 읽기에 대해 성능이 부족하므로 키의 유무를 체크하는것이 핵심
        - adaptive Radix Tree(ART), Hash index and bitmap 등과 같이 key 의 존재 유무를 체크하는것이 핵심

      
- Write Amplification
  - Write Amplification은 실제로 디스크에 쓰여지는 데이터 양이 애플리케이션에서 요청한 쓰기 데이터 양보다 몇 배 더 많아지는 현상을 말합니다.
  - LSM-tree는 데이터를 여러 레벨(L0, L1, L2...)에 저장하는데, 각 레벨간 병합(compaction) 과정에서 동일한 데이터가 여러 번 쓰여지게 됩니다.
  - 예를 들어:
    - 사용자 쓰기: 1KB
    - 실제 디스크 쓰기 과정:
    - 1. MemTable → SSTable(L0): 1KB 쓰기
    - 2. L0 → L1 compaction: 1KB + 기존 데이터 10KB = 11KB 쓰기  
    - 3. L1 → L2 compaction: 11KB + 기존 데이터 100KB = 111KB 쓰기
    - Write Amplification = 122KB / 1KB = 122배
  - 최적화 전략
    - Compaction 전략 개선
      - Leveled Compaction → Tiered Compaction 전환
      - Size-tiered 방식으로 같은 크기 SSTable끼리만 병합
    - Write Buffer 크기 조정
      - MemTable 크기 증가 → L0 SSTable 수 감소
      - 배치 처리로 compaction 빈도 줄이기
    - Bloom Filter 최적화
      - False Positive Rate 감소 → 불필요한 읽기/쓰기 방지

    - 고정 길이 chunk
      - 구현 및 데이터 관리가 용이
      - 처리가 단순하여 예측하기 쉬움
      - 중복된 청크가 존재할 가능성이 있어서 가변길이 chunk 보다 저장효율이 떨어짐
      - 단순히 고정 크기로 나누기 때문에 상대적으로 빠름
    - 가변 길이 chunk
      - 파일의 내용에 따라 chunk 의 크기를 달리 하여 전달
      - 별도 처리가 필요하므로 상대적으로 구현, 관리가 어려움
      - 중복된 청크를 또한번 저장할 필요없으므로 저장 효율이 높아짐
      - 성능보다 저장 효용성이 더 필요한 경우 선택
    - 가변길이 chunking 으로 중복제거시 hash 출돌이 발생하면?
      1. sha256 과 같은 보다 엄격한 hashing 사용
      2. 서버에서 hashing 처리시 이미 존재하면 실패후 다시 전송하도록 요청
      3. 기존 hashing 에 timestamp 와 같은 별도의 값을 추가하여 해당 경우에는 중복 청크 저장 허용
  - 보안
    - 각 chunk 마다 다른 key 를 사용하는지?
      - 파일 레벨로 Data Encryption Key 와 chunk 별 Intitialization Vector 를 조합한 하이브리드 방식
        - 하이브리드 방식
          - 파일별 고유 DEK: 각 파일마다 256비트 AES 키 생성
          - Chunk별 고유 IV: 각 청크마다 128비트 랜덤 IV 생성
          - 암호화 방식: AES-256-GCM (인증과 암호화 동시 제공)
        - 장점
          - 보안성: 동일한 내용의 청크라도 다른 파일에서는 다르게 암호화됨
          - 성능: 키 관리 오버헤드 최소화 (파일 수 << 청크 수)
          - 중복제거 호환: 같은 파일 내 동일 청크는 동일하게 암호화되어 중복제거 가능
    - 키 회전(Key Rotation) 전략
      - 계층적 키 회전 전략
        - KEK (Key Encryption Key) → DEK (Data Encryption Key) → 실제 데이터
          1. KEK 회전 (매년)
          2. DEK 회전 (분기별)
            - 새로운 업로드: 새 DEK 사용
            - 기존 데이터: 백그라운드에서 점진적 재암호화

  - object Key
    - UUID or snowflake?
      - 초기에는 단순히 UUID 를 사용하여 키를 구성했습니다. 다만 UUID 의 특설상 키가 문자열로 구성되어있고 아무래도 스트링 보단 단순 정수형으로 키를 구성하는게
      생대적으로 조회나 메모리 효율면에서 더 이득이 있을것 같아서 snowflake id 생성 방식으로 선택했었습니다.
      다만 지금 와서 생각해보면 snowflake id 생성 방식을 사용함으로써, 만일 metadata 서버가 오토스케일링으로 새로 뜰때마다 고유한 worker id 를 부여해야하고,
      이를 해결하기 위해 zookeeper, etcd 와 같은 별도 인프라를 사용하여 처리한다면 관리,운영포인트가 더 생기게 되어 오히려 마이너스일것으로 생각됩니다.
      그러므로 다시 UUID 를 사용하는게 좋지 않을까 합니다.
    - 시간순으로 정렬하는 ULID. 크기는 128비트로 UUID 와 동일하지만 앞부분 48비트는 밀리초 단위의 타임스탬프로 구성되어있고 나머지는 무작위 값이여서 앞부분을 사용하여 정렬가능
      - UUID (Random)의 경우: 새로운 객체가 생성될 때마다 완전히 무작위적인 ID가 생성됩니다. 데이터베이스의 Primary Key 인덱스(보통 B-Tree 구조)에 데이터를 삽입할 때, 이 새로운 ID는 인덱스 페이지의 무작위적인 위치에 들어가야 합니다. 이는 디스크 I/O를 유발하고, 페이지 분할(Page Split)을 빈번하게 일으키며, 캐시 효율을 떨어뜨리는 원인이 됩니다. 데이터가 많아질수록 쓰기 성능이 저하되죠.
      - ULID (Time-sortable)의 경우: 새로운 객체는 항상 시간적으로 가장 뒤에 생성되므로, ID 값 역시 기존 값들보다 항상 큽니다. 이는 인덱스 페이지의 가장 마지막에 순차적으로 데이터를 추가(Append-only)하는 것과 같은 효과를 냅니다. 디스크에 순차적으로 쓰기를 수행하므로 매우 빠르고, 페이지 분할도 거의 발생하지 않으며, 최신 데이터가 메모리 캐시에 남아있을 확률이 높아져 읽기/쓰기 성능 모두에 큰 이점을 가집니다.

  - NoSQL 을 선택한 이유?
    - 유연한 모델링과 확정성을 이유로 NOSQL 을 선택하였습니다.
    RDB 에 비해 스키마의 모델링이 자유로워 초기 구현에 이점이 있다는 점과, 샤딩 처리에 대한 유연함이 있기에 상대적으로 확장에 용이한 점이 있습니다.
    예를 들면 초기에는 지원하지 않는 기능들을 점차 하나씩 구현해나가면서 스키마를 변경해주어야 하는 RDB 와 달리 모델링이 자유롭다는 장점을 보았습니다.
    또한 설정이나 명령에 의해 샤딩처리와 동적 확장이 가능한 MongoDB 인 반면에 어플리케이션 레벨에서 직접 샤딩처리를 구현해야하는 번거로움이 존재합니다.
    다만 RDB 만큼의 강한 일관성을 보장해주지 않고 샤딩시 적절한 Key 선정을 고민해야하는 사항이 있지만 개인프로젝트에서 이러한 고민을 통해 스터디하는것이 좋을것 같아 선택하였습니다,
      - 일관성 문제에 대한 처리?
        - 서비스의 목적이나 관점에 따라 처리방법이 달라질것 같습니다.
        - Write Concern, Read Concern 
      - 내부 샤딩을 위한 Key 선택 전략?
        1. 먼저 고려해야 할 핵심 조건들
        샤딩 키를 정하기 전에 반드시 답할(또는 가정할) 항목들입니다. 이유가 설계에 직접 반영돼요.
        주요 쿼리 패턴: GET by object_id가 대부분인가? LIST by bucket/prefix가 많나? 메타검색(예: 태그/owner/created_at)도 자주 사용되나?
        버킷 분포 특성: 버킷당 객체 수가 균등한가? 소수의 핫(bucket)만 매우 큼? (ex: 일부 고객이 수백만 객체)
        읽기/쓰기 비율: 쓰기(업로드) 집중인가, 읽기(조회/리스트) 집중인가?
        일관성 요구사항: 강한 일관성 필요(단일 트랜잭션)인가 eventual OK인가?
        확장/리샤딩 편의성: 샤드 수를 동적으로 바꿀 가능성이 있는가?
        원소 삭제/GC/버전관리: TTL·라이프사이클 관리 방식
        NoSQL 선택지 특징: DynamoDB vs Cassandra vs MongoDB 등은 파티셔닝/인덱스 특성이 다름.
        설계는 “어떤 쿼리가 가장 많이 발생하느냐”가 최우선입니다.
        2. 흔히 쓰는 샤딩 전략(그리고 장단점)
            1. 단일 필드 해시 샤드 — hash(object_id) (가장 균형적)
                - 설명: 파티션 키에 object_id(또는 object_id의 해시)를 사용. 키는 랜덤(예: UUIDv4, SHA256(object_id))으로 분포시킴.
                - 장점
                  샤드 분포가 매우 고르게 됨 → hotspot 방지, 쓰기·읽기 분산 우수
                  GET by object_id가 O(1)으로 빠름
                  간단하고 확장(샤드 추가 시 라우팅 변경/consistent hashing 적용) 용이
                - 단점
                  LIST by bucket/prefix 가 비효율적: 한 버킷에 속한 모든 오브젝트를 찾으려면 별도 인덱스 필요(또는 전체 스캔)
                  버킷 내 정렬/범위 검색 불리
                  적합한 경우: 대부분 조회가 object_id 기반(예: CDN형 서비스, presigned URL 등), 버킷 리스트가 드문 경우
            1. 버킷 단위 파티셔닝 — bucket_id as partition key, object_name as clustering/sort key
                - 설명: 파티션 키 = bucket_id (또는 tenant_id+bucket_id), 정렬 키 = object_name/created_at
                - 장점
                LIST bucket/prefix scan/정렬 조회 매우 효율적 (한 노드에 몰려서 정렬 가능)
                범위검색(날짜순, 이름순) 쉬움
                - 단점
                특정 핫 버킷이 있으면 그 파티션에 모든 I/O 집중 → hotspot 발생
                스케일 아웃(버킷 단위로 샤드 나누기) 어려움(특히 NoSQL 시스템에서 파티션 키 기반의 동일 샤드로 모이는 성질 때문에)
                적합한 경우: 버킷당 객체 수가 작거나 균등하고 버킷 리스트가 매우 빈번한 경우
            1. 복합 키(버킷 + object_id hash) — bucket_id + hash(object_id) % k
                - 설명: 파티션 키를 bucket_id와 bucket_shard_id(예: hash(object_id) % S) 조합으로 만듦. S는 per-bucket shard 수(고정 또는 동적).
                - 장점
                큰 버킷을 여러 하위 샤드로 분산 가능 → hotspot 완화
                한 버킷 내부에서 분배되어 안정적 I/O
                - 단점
                LIST bucket을 할 때는 S개의 파티션을 병렬 조회해서 합쳐야 함 → 복잡한 페이징/병합 로직 필요
                S를 늘릴 때 기존 데이터 재배치 불가(혹은 복잡한 리샤딩 필요)
                적합한 경우: 일부 버킷이 매우 큰(수백만 객체)하고, 리스트도 필요하지만 분산도 필요할 때
            1. 별도의 버킷-인덱스(secondary index) 유지
                - 설명: 메인 테이블은 hash(object_id)로 구성(빠른 GET), 별도 테이블(또는 서비스)을 두어 bucket -> list(object_id chunks) 매핑을 유지.
                - 장점
                각 쿼리 패턴에 최적화된 테이블을 별도로 유지 가능 (격리된 확장성)
                리스트 성능 위해 shardable index 설계(예: bucket index를 여러 shard로 나눔)
                - 단점
                데이터 일관성·동기화 로직 필요(객체 생성/삭제 시 두 테이블 업데이트)
                복잡도 증가(트랜잭션 보장 어려움 시 eventual consistency 처리)
                적합한 경우: 읽기 패턴이 다양하고, GET/PUT/LIST를 모두 최적화해야 할 때
            1. Consistent hashing (Rendezvous hashing 등)
                - 설명: object_id(또는 bucket+object)로 consistent-hash를 돌려 메타 저장 노드(또는 노드 그룹)를 결정.
                - 장점
                노드 증설/감소 시 데이터 재분배 최소화
                분산 처리가 자연스럽게 됨
                - 단점
                구현·운영 복잡도(특히 메타 DB가 아닌 자체 라우팅 레이어를 쓸 때)
                적합한 경우: 자체 메타 서비스 + 많은 노드 동적 변경 경우
        3) 실무에서 많이 쓰는 하이브리드 패턴(권장 3가지 옵션)
            - Pattern 1 — (간단·범용): hash(object_id) as primary key + separate bucket-index table
                - 메인테이블 (빠른 조회)
                partition_key = object_id (or hash(object_id))
                columns = bucket_id, object_name, size, storage_class, created_at, checksum, version, file_offset...
                - 버킷 인덱스 (목록용; 샤딩 가능)
                partition_key = bucket_id or (bucket_id + shard_id)
                clustering_key = object_name or created_at
                value = object_id (포인터)
                - 장점: GET은 빠름, LIST도 별도 인덱스로 최적화 가능, 버킷 핫스팟은 인덱스에서 샤딩으로 제어 가능
                - 단점: 쓰기 시 두 테이블 업데이트 요구(트랜잭션 필요하면 복잡)
            - Pattern 2 — (리스트 우선): bucket_id as partition key + object_name sort key
              - 장점: LIST·prefix 스캔 매우 빠름; 구현 단순
              - 단점: 핫 버킷 문제. 해결하려면 bucket-level sharding (Pattern 3) 고려
              언제 추천: 고객 버킷이 균등하고 리스트 요청이 많을 때
            - Pattern 3 — (대형 버킷/혼합 워크로드): bucket_id + bucket_shard as partition key
            bucket_shard = hash(object_id) % S (S는 고정 혹은 bucket별 가변)
            LIST 구현: parallel query across S shards + merge/paginate
            장점: 큰 버킷도 분산 가능, GET 용이(need local routing to specific shard)
            단점: LIST 복잡성·페이징 처리 복잡, S 변경 시 어려움
            팁: S를 미리 꽤 크게 잡아두고(예: 8, 16) 운영 중 모니터링 → 필요시 bucket-specific shard mapping 도입
            샤드 키 후보: { object_id: 1 } 또는 { bucket_id: 1, shard_id: 1, object_name: 1 }
            주의: 몽고는 샤드 키 선택이 중요(변경 불가), 몽고에서는 자주 리스트 한다면 bucket 포함한 복합 샤드 키를 고려하되 hotspot 체크 필요
        5) 보조 고려사항 & 실무 팁
            - 키 생성: object_id는 UUIDv4 또는 랜덤 해시를 권장(숫자 오름차순 ID/타임스탬프 기반 키는 쓰기 hotspot 유발).
            만약 시간순 정렬 필요하면 ULID/KSUID(시간 + 랜덤)을 쓰되, 샤드 키로는 해시를 사용하거나 bucket+clustering으로 사용.
            - Salt(키 염색): 리스트는 필요한데 버킷이 일부 핫하다면 object key 앞에 salt(0..N-1) prefix를 붙여 쓰기 분산 → 읽을 때는 해당 N개를 병렬조회.
            - 페이징: bucket-list 페이징은 각 shard마다 cursor를 유지(각 샤드의 last-key)하고 병합해서 사용자 토큰으로 반환(다소 복잡).
            - 일관성/동기화: 메인 테이블 + bucket-index 사용 시, PUT/DELETE 시 두 테이블을 동일하게 업데이트해야함. 트랜잭션이 지원되지 않으면 eventual consistency와 보정(스케줄러로 scan/repair)을 도입.
            - GC/삭제 처리: 삭제 시 tombstone 기록 + background compaction/cleanup. 대량 삭제(버킷 삭제)는 병렬 처리로 진행.
            - 메타 크기 & 폭주 방지: 메타 항목이 커지면 NoSQL 비용(읽기/쓰기 용량) 증가. 조회 패턴에 맞춰 필요한 필드만 저장.
            - 모니터링 지표: 파티션별 IOPS, 읽기/쓰기 레이턴시, 핫 파티션 비율, 분포도(Top-K partitions) — 지표로 hotspot 감지 및 shard 수 조정.
            - 검색(메타속성 기반): 태그/owner/metadata search 는 Elasticsearch 같은 검색전용 색인을 사용하길 권장(관계형 인덱스 아님).
        6) 결론 및 권장 기본안 (범용)
            - 기본 권장(안정·확장성·구현 난이도 균형):
            - 메인 테이블: partition_key = hash(object_id) (object_id는 UUID 또는 랜덤 해시) — GET에 최적화
            - 버킷 인덱스 테이블: partition_key = bucket_id OR bucket_id#shard_id(버킷별 샤드) — LIST에 최적화
            - 작은/중간 버킷이면 bucket_id만으로, 큰/불균형 버킷이 예상되면 bucket_id#(hash(object_id)%S) 사용
            - 쓰기 시: 트랜잭션이 없다면 두 테이블을 쓰고(메인·인덱스), 실패 시 보정(리트라이/repair job)
            - 페이징: bucket-list는 shard별 병렬 쿼리 + merge 페이징(커서 포함) 구현
            - 왜 이게 좋나: GET 빠르고 샤드 분배 균형 유지, LIST도 별도 인덱스로 최적화 가능. 대부분의 실제 시스템(예: S3 구현체, 대형 오브젝트 스토어)가 이 모델을 채택합니다.
        7) 빠른 체크리스트 (설계/배포 전에)
            - 주요 쿼리 비율(%) 측정 → 샤드키에 반영
            - 예상 최대 객체수/버킷별 분포 산정
            - 샤드 수와 per-shard 처리량(예상 RPS) 계산
            - 장애 시 복구/repair 절차 문서화
            - 모니터링과 자동 알람(핫스팟 감지) 구축

- Storage
  - linux 환경에서 file write/read
    - file write 시 O_APPEND 옵션을 사용하여 파일의 현재 끝 위치로 커서(offset)를 자동으로 이동시킨 뒤 데이터를 기록합니다.
      - 내부적으로는 커널 수준에서 원자적으로 현재 파일 크기를 확인하고, 데이터를 그 위치에 덧붙이는 작업이 이루어집니다.
        - 커널 내부에선 write 시 해당 파일의 inode 에 대해 락을 획득하고 이후 파일 크기를 조회하여 커서를 끝으로 이동후 wrtie 함
        - inode 에 파일별 뮤텍스로 인해 파일락을 통해 동시 접근에 대해 write 시 원자성을 보장하고 있음
        - 그러나 반대로 여러 프로세스에서 동시에 write 시 경합으로 인해 성능 병목이 생길수 있음
          - 먼저 WAL 과 같은 다른곳에 저장하고 추후 flush 하는 등의 최적화
      - 여러 프로세스가 동일한 파일에 대해 처리한다면 O_APPEND 사용시 파일 끝 위치 갱신이 직렬화되기 때문에 race condition 을 방지할수 있음
        - 중요한 점은 O_APPEND는 데이터 일관성을 위해 파일 끝 위치 갱신을 원자적으로 처리하도록 락을 쓰지만, 다수 동시 쓰기 시 락 경합 때문에 성능에 약간의 영향을 줄 수 있다는 점입니다.
        - 따라서 초당 엄청난 동시 쓰기가 일어나는 상황이라면 추가적인 락 분산, 파티셔닝, 버퍼링 전략 등을 고려해야 합니다.

네, 시스템의 한계를 인지하고 전체적인 구조 변경을 고민하시는 점,
그리고 데이터 관리의 책임을 별도의 컴포넌트로 분리하려는 방향성은 아주 좋은 접근입니다. 문제의 핵심을 잘 파악하고 계십니다.

다만, 여기서 핵심적인 질문은 "분리된 그 거대한 블록 리스트를 어디에, 어떻게 저장할 것인가?" 입니다.
RDB를 도입하여 데이터 노드와 객체를 관리하는 것도 하나의 방법이 될 수 있지만,

요청하신 대로 모범 답변의 형태로 이 패턴을 설명해 드리겠습니다.

모범 답변 예시
이 '거대 메타데이터' 문제에 대한 가장 효과적이고 확장 가능한 해결책은 '목록 파일(Manifest File)' 또는 '인덱스 객체(Index Object)' 패턴을 사용하는 것입니다.

아이디어는 간단합니다. 수만 개의 블록 ID 리스트를 원본 객체의 메타데이터에 직접 저장하는 대신, 그 리스트 자체를 하나의 새로운 객체로 만들어 저장하는 것입니다.

동작 방식:
파일 분할: 사용자가 100GB 파일을 업로드하면, 시스템은 이전과 동일하게 파일을 여러 개의 블록(예: 4MB짜리 블록 25,600개)으로 분할하여 각각 데이터 스토리지에 저장합니다.

목록 파일(Manifest) 생성: 시스템은 이 25,600개 블록의 ID와 순서가 담긴 목록(Manifest)을 내용으로 하는 새로운 객체를 하나 생성합니다.
이 목록 파일 객체 역시 데이터 스토리지에 저장됩니다.

원본 메타데이터 업데이트: 이제 원본 객체(100GB 파일)의 메타데이터에는 더 이상 긴 블록 리스트가 들어가지 않습니다.
대신, 방금 생성한 '목록 파일 객체의 ID' 와 파일이 여러 조각으로 나뉘었다는 표시(플래그)만 간단하게 저장합니다.
결과:

메타데이터 크기 문제 해결: 원본 객체의 메타데이터는 파일 크기와 상관없이 항상 작고 일정한 크기를 유지하게 됩니다.
MongoDB의 16MB 문서 크기 제한과 같은 문제를 완벽하게 피할 수 있습니다.

확장성: 이 방식은 재귀적으로 적용될 수 있습니다.
만약 파일이 너무 커서 목록 파일 자체의 크기가 문제가 될 정도라면, '목록 파일의 목록 파일'을 만드는 식으로 무한히 확장이 가능합니다.

일관된 아키텍처: 새로운 종류의 데이터베이스(RDB)를 도입할 필요 없이, 모든 것을 '객체'라는 단일 개념 안에서 처리할 수 있어 시스템의 복잡도가 낮아집니다.
이 방식은 실제로 AWS S3의 멀티파트 업로드(Multipart Upload) 기능이 동작하는 핵심 원리와 매우 유사합니다.
이처럼 시스템의 기본 구성 요소를 활용하여 문제를 해결하는 것이 더 우아하고 확장성 있는 설계로 이어지는 경우가 많습니다.

해당 방법에 대해 어떠한 장단점이 있고 한계가 있을까?

네, 아주 예리한 질문입니다. 어떤 기술이든 장점만 있는 '은총알'은 없죠. 이 '목록 파일(Manifest File)' 패턴의 장단점과 그에 따른 한계를 정확히 파악하는 것이 중요합니다.

장점
압도적인 확장성 (Massive Scalability): 앞서 이야기한 것처럼, 메타데이터 크기 제한 문제를 해결하여 사실상 무한한 크기의 파일을 지원할 수 있게 됩니다.
이것이 이 패턴을 사용하는 가장 큰 이유입니다.

병렬 다운로드/스트리밍 최적화 (Parallel Download/Streaming): 클라이언트는 목록 파일을 먼저 받은 뒤, 그 안에 있는 블록 리스트를 보고 여러 블록을 동시에 병렬로 요청할 수 있습니다.
이는 대용량 파일의 다운로드 속도를 획기적으로 높여줍니다.

아키텍처의 일관성 유지 (Architectural Consistency): 새로운 컴포넌트나 데이터베이스를 도입하는 대신, '객체'라는 기존 시스템의 기본 단위를 재활용합니다.
이는 시스템의 복잡도를 낮추고 유지보수를 용이하게 합니다.

단점 및 한계
읽기 증폭 (Read Amplification): 가장 큰 단점입니다. 파일을 읽기 위해 최소 두 번의 읽기 작업이 필요합니다.
첫 번째는 '목록 파일'을 읽는 작업, 두 번째는 그 목록을 보고 실제 '데이터 블록'을 읽는 작업이죠.
이는 특히 파일의 특정 부분만 조금 읽으려고 할 때(Range-based Read) 지연 시간(Latency)을 증가시키는 요인이 됩니다.

원자성(Atomicity) 보장의 복잡성: 객체를 삭제하거나 수정할 때 문제가 복잡해집니다.
예를 들어, 객체를 삭제하려면 '목록 파일 객체'와 그에 연결된 수많은 '데이터 블록 객체'들을 모두 삭제해야 합니다.
이 과정 중간에 시스템 장애가 발생하면, 일부 블록만 삭제되거나 혹은 아무도 참조하지 않는 '고아 블록(Orphan Block)'이 남아 저장 공간을 낭비하게 될 수 있습니다.
이런 작업을 원자적으로 처리하기 위한 추가적인 로직(예: 별도의 가비지 컬렉션 프로세스)이 필요합니다.

작은 파일에 대한 오버헤드 (Overhead for Small Files): 굳이 나눌 필요가 없는 작은 파일에 이 패턴을 적용하면, 불필요한 목록 파일을 만들고 읽기 증폭만 유발하는 비효율이 발생합니다.
따라서 보통은 특정 크기(임계값) 이상의 파일에만 이 패턴을 적용하는 방식으로 구현합니다.
결론적으로, 이 패턴은 대용량 파일 처리에 필수적인 강력한 확장성을 제공하지만, 그 대가로 읽기 지연 시간 증가와 데이터 관리의 복잡성이라는 트레이드오프를 감수해야 합니다.
